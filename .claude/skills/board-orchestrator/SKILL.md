# board-orchestrator — Cera 기능 하네스

리더(메인 세션)가 이 절차를 돈다. 역할을 나누는 이유는 앵커링을 피하기 위해서다(구현자가 자기 코드를 리뷰하지 않는다, 코드를 읽은 에이전트는 사용성을 말하지 않는다, 사용감의 마지막 판정은 사람이 한다).

**무엇을 위해 만들고 무엇으로 판정하나:** `references/eval-goals.md` — 용도 U1–U4 와 평가 축 A(코드) · B(에이전트 상호작용) · C(처음 써 보는 사람) · D(사람). 계획 · 리뷰 · 보고는 이 파일의 번호(U · N · H)를 가리킨다.

## 효율 규칙 (모든 단계에 적용)
- **리더의 컨텍스트를 아낀다.** 에이전트의 반환 메시지는 5줄 이하, 경로 + 판정 + 개수만. 리더는 보고 파일을 통째로 읽지 않고 필요한 절만 `grep`/`sed` 로 본다.
- **프롬프트는 파일을 가리킨다.** 계획 · 기준 · 이전 지적을 프롬프트에 다시 쓰지 말고 `_workspace/` 경로와 절 이름만 준다.
- **보고 파일 상한:** 구현 보고 ≤ 30줄, 리뷰 ≤ 40줄(지적 ≤ 12개, 각 ≤ 3줄), 처음 써 보는 사람 리뷰 ≤ 30줄, 스모크 · 실측 ≤ 20줄씩, 계획 ≤ 150줄. 긴 로그 · 스크린샷 설명은 파일 경로로 대신한다.
- **이어 부르기:** 고침은 같은 구현자에게, 다음 라운드는 같은 리뷰어 · 같은 시험자에게 SendMessage 로 이어서 보낸다(새 에이전트를 만들지 않는다).
- 새로 만든 `.claude/agents/*.md` 가 subagent_type 으로 잡히지 않거나 ocx 모델로 부를 때는, 첫 줄에 "너는 `.claude/agents/<역할>.md` 의 역할이다. 그 파일과 스킬을 먼저 읽어라" 를 넣는다.

## 역할과 산출물

| 단계 | 역할(1순위 모델) | 산출물 |
|---|---|---|
| 0 맥락 | 리더 | `_workspace/00_context.md`(≤ 40줄, 모델 경로 한 줄 포함) |
| 1 조사(선택) | board-scout × 1–3 | `01_scout_<lens>.md` |
| 2 고르기 · 나누기 | board-orchestrator(또는 범위가 정해졌으면 리더) | `02_plan.md`(WP 마다 용도 U 번호) |
| 3 구현 | board-implementer × WP | 코드 + `03_impl_WP-n.md` |
| 4 적대적 리뷰(축 A) | **neon** + **Opus medium**, `board-reviewer` 역할 | `04_review_WP-n_<모델>_r<k>.md` |
| 5a 스모크 · 실측(축 B) | 잡일 담당 **hydrogen 또는 Luna**, `board-uiux-tester` 역할 | `05_smoke.md`, `05_metrics.md` |
| 5b 처음 써 보는 사람 리뷰(축 C) | **hydrogen + Luna**, `board-uiux-tester` 역할(코드를 읽지 않음) | `05_naive_<모델>_r<k>.md` |
| 5c 사람 UX 확인(축 D) | 리더 → **사용자** | `05_ux_request.md` → `05_ux_human.md` |
| 6 판정 · 통합 | 리더 | 커밋(브랜치), 보고 |

## 모델과 대체 순서

| 자리 | 1순위 | neon 을 못 쓸 때 | ocx 가 통째로 안 될 때 |
|---|---|---|---|
| 코드 리뷰 ① | neon `ocx-gemini-4-neon` | hydrogen `ocx-gemini-4-hydrogen` + Luna `ocx-gpt-6-luna`(둘 다) | Codex `codex:codex-rescue` |
| 코드 리뷰 ② | Opus medium(`general-purpose`, model `opus`, effort `medium`) | 그대로 | 그대로 |
| 잡일(스모크 · 로그 모으기 · fixture 만들기) | hydrogen 또는 Luna | 그대로 | 리더가 스크립트를 직접 돌린다(출력은 파일로, 끝 몇 줄만 본다) |
| 처음 써 보는 사람 리뷰 | hydrogen + Luna | 그대로 | Opus medium 새 에이전트 하나(코드 리뷰어와 다른 에이전트) |

- **Haiku 는 어느 자리에도 쓰지 않는다.** ocx 에이전트를 부를 때 `model` 인자는 넣지 않는다(프록시가 모델을 고정한다).
- **ocx 가 되는지는 Phase 0 에서 한 번만 확인한다.** neon · hydrogen · Luna 에 "OK 한 단어로 답하라" 를 동시에 보내고 결과를 `00_context.md` 에 `모델 경로: neon 됨/안 됨 · hydrogen … · Luna …` 로 적는다. `model_not_found` 는 세션을 opencodex 로 띄우지 않았을 때 난다 — 다시 시도하지 않고 오른쪽 칸으로 간다. 에이전트 종류 목록에 이름이 없을 때도 같다.
- hydrogen · Luna 중 하나만 되면 되는 쪽이 두 자리를 맡되, 처음 써 보는 사람 리뷰의 나머지 한 자리는 Opus medium 새 에이전트로 채운다.
- **Codex 로 리뷰할 때:** 같은 입력(diff 범위 + 계획 절)을 주고 보고 파일 하나만 쓰게 한다. 코드 수정 · 커밋 · 삭제는 맡기지 않는다. Codex 의 막음/고침은 Opus 리뷰어에게 이어 보내 파일:줄을 재현으로 확인한 뒤에 구현자에게 넘긴다.
- 대체를 썼으면 리뷰 파일 이름의 `<모델>` 과 Phase 6 보고에 그대로 적는다(예: "WP-2 r1: neon 안 됨 → hydrogen + Luna").

## Phase 0 — 맥락
- 새 주제면 `_workspace` 를 `_workspace_prev` 로 옮긴다. 기본 브랜치면 `feat/<주제>` 를 만든다.
- `00_context.md`: 요청 원문, 관련 파일 목록, 제약(링크 하나로 바로 · 폰 · 임시 보드 · 표준 라이브러리 서버 · 라이선스 · 유료 API 없음), 이번 일이 닿는 용도(U 번호), 모델 경로.

## Phase 1 — 조사 (필요할 때만)
- 사용자가 외부 조사 · 벤치마킹을 요청했거나, 구현 경로를 모를 때만 한다. 기본 1–2 lens, 최대 3.

## Phase 2 — 고르기 · 나누기
- 사용자가 범위를 정했으면 리더가 직접 `02_plan.md` 를 쓴다. 아니면 board-orchestrator 를 한 번 부른다.
- WP 마다 목적 · 용도(U) · 파일 · 받아들일 기준(시험 가능한 문장) · 의존 · 병렬 묶음. 같은 파일(`server.py` · `tb_mcp.py` · `Board.jsx`)을 만지는 WP 는 차례로.
- 에이전트 연동을 건드리는 계획은 축 B 의 어느 측정이 달라지는지 한 줄 적는다.

## Phase 3–4 — 구현과 적대적 리뷰 (WP 마다)
1. 구현자가 끝내면 **리뷰어들을 동시에** 부른다(위 표의 ① + ②). 모두 `board-reviewer.md` 역할, 입력은 diff 범위 + `02_plan.md` 의 그 WP 절 + `eval-goals.md` 의 A 표 + (r2 부터) 이전 지적 파일. 구현 보고는 주지 않는다.
2. 리뷰들의 `막음/고침` 을 합쳐(중복은 하나로) 같은 구현자에게 넘긴다.
3. 다음 라운드는 **고친 부분의 diff 와 이전 지적만** 같은 리뷰어들에게 다시 보낸다. 모두 `막음 0 · 고침 0` 이면 그 WP 는 통과.
4. 최대 3라운드. 3라운드 뒤에도 막음이면 리더가 빼기 · 미루기를 정하고 보고에 적는다. 리뷰어들이 서로 반대로 판정하면 재현 시험(코드 · 명령)으로 가린다 — 말로 다수결하지 않는다.

## Phase 5 — 스모크 · 실측, 처음 써 보는 사람, 사람 UX 확인
- **5a 스모크 · 실측(잡일 담당 하나):** `board-uiux-test` 스킬의 스크립트(`ui_smoke.py` 4기기 + 기능별 live 스크립트)를 돌려 통과/실패를 `05_smoke.md` 에. 에이전트 연동이 바뀌었으면 `eval-goals.md` B 표를 잰다: ① 잡일 담당이 보드를 띄워 고정 자료를 올리고 요청을 걸어 둔다 → ② 리더가 맥락 없는 판독 에이전트(Opus medium 은 꼭, 되면 Luna · hydrogen 도)를 불러 MCP 로 요청을 처리하게 한다 → ③ 같은 잡일 담당에게 이어 보내 채점하고 `05_metrics.md` 에 적게 한다. 실패가 있으면 5b 로 가지 않고 Phase 3 으로.
- **5b 처음 써 보는 사람 리뷰(둘 동시에):** `eval-goals.md` C 표의 과제 문장만 주고, 띄워 둔 보드 링크와 보고 경로를 준다. 계획 · diff · 리뷰 파일은 주지 않는다. '안 됨' 과 두 쪽이 같이 짚은 곳은 Phase 3 으로, 한쪽만 짚은 곳은 5c 의 질문 후보로. 고친 뒤에는 실패한 과제만 같은 에이전트에게 다시 시킨다(최대 2라운드).
- **5c 사람 UX 확인(사용자):** 리더가 `eval-goals.md` D 표에서 골라 `05_ux_request.md` 를 만든다 — 열어 볼 링크(로컬 보드, 필요하면 임시 터널), 해 볼 일 ≤ 10개, 답 칸(좋음/이상함/안 됨 + 한 줄). 사용자에게 **5줄 이하로** 요청하고, 답을 `05_ux_human.md` 에 옮긴 뒤 '안 됨 · 이상함' 만 Phase 3 으로 돌린다. 5b 의 결과나 에이전트의 짐작으로 UX 를 '통과' 로 적지 않는다. 답이 없으면 '확인 못 함'.

## Phase 6 — 통합
1. `cd web && npm test && npx vite build`, `python3 -m unittest discover -s tests -q`, `/usr/bin/python3 -m unittest discover -s tests -q`, `python3 packaging/gen.py --check`, `claude plugin validate .` 통과.
2. 버전(plugin.json → `packaging/gen.py`, web/package.json · lock 루트 두 곳). README 는 짧게 유지, 세부는 docs/guide.md.
3. 브랜치에 커밋. **push · release 는 사용자가 요청할 때만.** 보고: 넣은 것 / 미룬 것 / 축 A–D 판정(`eval-goals.md` 3절 표 형식) / 쓴 모델과 대체 / 확인 못 한 것.

## 비용 상한
조사 ≤ 3 + 계획 ≤ 1 + 구현 WP 수 + 리뷰 (2–3 × WP 수 × 라운드 ≤ 3) + 잡일 1 + 처음 써 보는 사람 2(× 라운드 ≤ 2) + 판독 1–3. 라운드는 같은 에이전트를 이어 쓰므로 새 컨텍스트를 만들지 않는다.

## 에러 핸들링
- 에이전트 실패 → 1회 재시도, 다시 실패하면 '모델과 대체 순서' 표의 다음 칸으로 가고 보고에 적는다. 대체까지 실패하면 그 결과 없이 진행하고 '확인 못 함' 으로 적는다.
- 시험 스크립트 탓인지 앱 탓인지 모르면 재현 명령으로 가린다.

## 테스트 시나리오
- **정상:** "수식 손글씨 변환 넣어 줘" → 리더가 계획(WP 3, U2) → WP 마다 구현 → neon + Opus medium r1 지적 4 → 고침 → r2 둘 다 0 → Luna 가 스모크 · 실측(수식 3/4, 왕복 22초, 호출 5) → hydrogen + Luna 가 N3 · N4 를 해 보고 "요청 버튼을 못 찾음" 을 같이 짚음 → 고침 → `05_ux_request.md` 로 사용자에게 H3 · H6 · H7 확인 요청 → '폰에서 버튼이 가려짐' → 고침 → 커밋.
- **대체:** Phase 0 확인에서 셋 다 `model_not_found` → 코드 리뷰는 Codex + Opus medium, 잡일은 리더가 직접, 처음 써 보는 사람 리뷰는 Opus medium 새 에이전트 → 보고에 "ocx 안 됨" 한 줄.
- **에러:** WP-2 가 3라운드 뒤에도 막음 → 리더가 미룸으로 정하고 나머지만 통합.
- **부분 재실행:** "UX 확인 요청 다시 만들어" → `05_ux_request.md` 만 다시 쓴다. "처음 쓰는 사람 리뷰 다시" → 5b 만.
